# PromptMatrix Pro — 自动化发布方案设计

> 版本：v1（设计稿，未实现）
> 日期：2026-07-15
> 范围：打通「生成 → 审核 → 发布 → 监测」闭环，重点解决两件事——(1) 用 LLM API 替代人工复制粘贴生成；(2) 把最终稿真正发到目标平台。
> 当前约束：**用户暂无任何平台的自动发布资质**（微信认证服务号 / 小红书专业号 / 百家号 / 头条号 均没有），因此官方 Open API 路线暂时不可行，发布侧只能先做 LLM 生成自动化 + Playwright 兜底，或保持人工。

---

## 0. 背景与现状

### 0.1 现有生产流程（10 步）
1 行业 → 2 平台 → 3 定人设账号 → 4 目标客户需求(GEO) → 5 关键词/知识点
→ 6 大纲(outline) → 7 初稿(draft) → 8 洗稿精修(rewrite) → 9 安全发布&GEO筛选(geo) → 10 配图(illustration)

第 9 步 `geo-finalize` 已能产出「可直接发布形态」：`final_title` + `final_content`（纯文本/HTML）。

### 0.2 现状缺口（已确认）
- **后端无任何 LLM 调用**。当前模式是：前端生成提示词 → 用户手动复制给 AI（网页/客户端）→ 把 AI 结果手动粘贴回系统。生成环节完全靠人肉中转。
- **`publish_task` 只做内部登记**：在 `ProductionTask` 上写 `publish_url`（由用户手动回填），并生成一条内部 `ContentAsset` 记录。**系统本身从未真正调用任何平台接口去发布**。
- 因此"发到平台上"这一步，今天 100% 是人工：复制标题/正文 → 打开平台后台 → 粘贴 → 点发布 → 把链接回填。

### 0.3 本次目标
把上述两处人工中转自动化，同时**保留人工审核闸门**（图里琥珀色节点），避免无脑群发对 GEO 反噬。

---

## 1. 总体架构

```
生产任务 → 渲染提示词(注入平台/品牌变量)
        → [LLM API 生成]  DeepSeek(可插拔:OpenAI/本地)
        → [结构化解析]     geo-finalize / rewrite-import
        → [人工审核闸门]   合规·GEO评分须过线(建议保留)
        → [平台发布器 PlatformPublisher]
             ├─ 官方 Open API   : 微信·小红书·百家号·头条  (需认证资质)
             └─ Playwright 兜底 : 知乎·搜狐·网易          (ToS风险)
        → 平台(已发布)
        → 回写 publish_url + 触发 GEO 监测
```

设计原则：
- **生成**与**发布**两套能力解耦，可分别上线。
- **提供方/平台可插拔**：LLM 不止 DeepSeek，平台不止一种。
- **凭证不下库明文、不进 git**。
- **审核闸门默认在**：首次发布前必须人工批准，之后可配置为可信后跳过。

## 2. LLM 生成自动化（阶段 0，最先落地，零资质依赖）

这是当前**唯一无需任何外部资质**即可开工的部分，直接消除"复制粘贴给 AI"这一步。

### 2.1 提供方抽象 `LLMProvider`
统一接口，屏蔽不同厂商差异：

```python
class LLMProvider(ABC):
    @abstractmethod
    def generate(self, prompt: str, *, temperature=0.7,
                 max_tokens=2000, step: str = "") -> str: ...

class DeepSeekProvider(LLMProvider):   # OpenAI 兼容协议
    base_url = "https://api.deepseek.com/v1"
    # chat/completions, model="deepseek-chat"

class OpenAIProvider(LLMProvider): ...
class LocalProvider(LLMProvider): ...  # 预留 ollama / vllm
```

`generate()` 返回纯文本；若调用的是第 9 步 geo 提示词，返回的就是四段结构（标题/正文/评分/建议），直接喂给 `geo-finalize` 解析；若是第 8 步 rewrite 提示词，返回纯文本正文，回填文本框。

### 2.2 凭证与配置存储
- 新增配置表 `llm_config`（或加密的 settings 表），字段：`provider, base_url, api_key(加密), model, temperature, max_tokens, is_default`。
- 密钥加密存储（如 `cryptography.fernet`），**绝不硬编码进代码、绝不进 git**。
- 环境变量兜底：`DEEPSEEK_API_KEY` 等，便于部署。
- 提供「测试连接」按钮，保存前验证 key 可用。

### 2.3 新增端点
```
POST /api/llm/generate
  body: { prompt: str, provider?: str, step?: str, task_id?: int }
  return: { text: str, provider: str, model: str, tokens: int }
```
- `prompt` 由前端调用现有 `build_render_context` 渲染好后传入（复用现有强耦合提示词，不动提示词体系）。
- 失败处理：超时/限流自动重试（指数退避），最终失败返回明确错误，前端回退到「手动复制」模式。

### 2.4 前端改造
- 每一步（outline/draft/rewrite/geo）的「复制给 AI」按钮旁，增加**「一键生成」**：
  - 点击 → 调 `/api/llm/generate` → 结果自动填入对应文本框。
  - 第 9 步：生成结果直接进 `geo-finalize` 解析 → 渲染可复制标题/正文。
  - 第 8 步：生成结果回填洗稿文本框（沿用当前纯文本模式）。
- 保留「手动模式」入口，LLM 不可用时无缝降级。

### 2.5 成本与可控性
- DeepSeek `deepseek-chat` 价格极低（约 ¥1/百万 tokens 级），单篇软文成本可忽略。
- 每任务记录 token 消耗，便于核算。

## 3. 平台发布器 `PlatformPublisher`

### 3.1 抽象层
```python
class PlatformAdapter(ABC):
    platform: str                       # wechat / xiaohongshu / baijiahao / toutiao / zhihu / sohu / wangyi
    @abstractmethod
    def publish(self, title: str, content: str,
                cover: str | None, cred) -> PublishResult: ...
    # PublishResult: { url: str, status: str, raw: dict }

class PlatformPublisher:
    def __init__(self): self._adapters = {a.platform: a for a in [...]}
    def publish(self, platform, *args):
        return self._adapters[platform].publish(*args)
```

### 3.2 官方 Open API 适配器（需资质，当前用户暂无）
| 平台 | 接口 | 所需凭证 | 备注 |
|---|---|---|---|
| 微信公众号 | 素材 `add_news` + 发布 `freepublish/submit` | 认证服务号 `appid/appsecret` | 最成熟，支持图文+封面 |
| 小红书 | 开放平台专业号 `note_publish` | 专业号 `app_id/app_secret` + token | 需专业号认证 |
| 百家号 | 百度百家号开放平台内容发布 API | `client_id/secret` + token | — |
| 头条/抖音 | 头条开放平台文章发布 | `client_key/secret` + token | — |

- 凭证存 `platform_credential` 表（加密），按 platform 关联。
- **当前用户无上述资质，此路线暂缓**，待资质到位后按表实现即可，抽象层已预留。

### 3.3 Playwright 浏览器自动化适配器（无 API 平台的兜底）
适用：知乎 / 搜狐 / 网易（无开放发布 API）。
```
登录态加载(cookie 文件) → 导航发布页 → 填标题/正文(富文本) → 传封面
→ 提交 → 等待发布成功 → 取回文章 URL
```
关键工程点：
- **登录态管理**：首次人工登录后导出 cookie 持久化；过期时标记 `needs_relogin` 并告警，由人工续期（不自动破解 2FA）。
- **稳健选择器**：优先用 `data-*` / 稳定 class，避开易变结构；关键步骤加显式等待。
- **失败兜底**：超时/验证码/未知弹窗 → 截图存证 + 任务标记 `failed` + 通知。
- **频率与错峰**：每平台最小间隔（如 ≥10 分钟），避免触发风控。

**风险提示（务必知会决策方）**：各平台 ToS 普遍禁止自动化批量发布营销内容，存在限流/封号风险；且对 GEO 可能反噬（低质自动内容被降权）。**仅作为无 API 平台的最后手段，且需人工知情授权。**

## 4. 人工审核闸门（建议保留）

发布不是无脑全自动，引入 `publish_job` 状态机：
```
draft → pending_review → approved → publishing → published
                                  ↘ rejected(打回)
                            publishing → failed(可重试)
```
- **审核页**：预览标题/正文/目标平台、展示 GEO 评分与安全合规结论、一键「批准发布」或「打回修改」。
- 可配置策略：`首次必审` / `可信模板后可跳过` / `全部自动`。
- 这是防止 GEO 反噬与违规发布的核心保险。

---

## 5. 调度与批量

- `publish_job` 支持 `scheduled_at`：可排期错峰发布。
- 全局频控：每平台最小间隔、每日上限。
- 失败重试（有限次）+ 告警（站内/Webhook）。
- 运行期日志：每次发布留痕（平台/时间/URL/耗时/token）。

---

## 6. 凭证与安全管理

- 所有密钥（LLM api_key、平台 appsecret、cookie）**加密存储**（Fernet/AES），明文不落库、不进 git。
- 最小权限：平台账号仅授予发布所需角色。
- 密钥轮转：支持重新录入并失效旧值。
- 审计：凭证的增改删留痕。

---

## 7. GEO 风险与建议

系统本质是 GEO/AEO——让 AI 在用户提问时推荐并引用你们。需注意：
- **全自动群发可能反效果**：平台判低质/营销 → 降权；AI 检索把软文当噪音。
- 建议：**保留审核闸门**、内容质量优先于数量、发布节奏拟人化。
- 发布后联动已有 `GeoMonitor`：监测是否真被 AI 引用，形成「发布→监测→补缺口」闭环。

## 11. 当前约束下的最小可行路径（结论）

因为**暂无任何平台资质**：
- **阶段 0（生成自动化）可立即开工**，零外部依赖，先消除复制粘贴。建议作为第一步。
- **发布侧**：官方 API 路线暂缓至资质到位；在此之前若要"真自动发"，只能走 Playwright 兜底（阶段 2），但须决策方明确知悉 ToS/封号风险并授权；否则发布维持人工、仅做生成自动化。
- 无论哪条路，**审核闸门与凭证加密**都是必备项，不可省略。
